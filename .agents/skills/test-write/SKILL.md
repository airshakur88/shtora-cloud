# Test Write

Generate pytest tests that meet the high-value rubric: focused, deterministic, readable, fast, behavior-bound.

Scope: Python / pytest only.

## Step 1: Read the target

1. **Resolve `$ARGS`.** It is one of:
   - A file path (e.g. `src/myapp/orders.py`) → test everything public in the file.
   - A dotted path (e.g. `myapp.orders.place_order`) → test that single symbol.
   - A natural-language description → ask the user for a concrete target first; do not invent one.

2. **Read the source.** Note:
   - Public API (no `_` prefix).
   - Argument types and defaults.
   - Every `raise` — each is a contract.
   - Every branch that changes an observable outcome.
   - Every documented exception in the docstring.
   - External collaborators (network, DB, clock, random, filesystem).

3. **Detect the pytest invocation prefix** the same way `test-review` does: find the pytest config root (pyproject.toml / pytest.ini / setup.cfg / tox.ini), then pick `uv run pytest` / `poetry run pytest` / `pipenv run pytest` / bare `pytest` based on the tooling markers in that root. Prefix with `cd <root> &&` if the config root is not the repo root. Store the prefix for Step 5.

## Step 2: Inventory existing fixtures

Walk up from the target's test directory to the repo root, reading every `conftest.py`. Collect:

- Fixture names and what they return.
- Existing autouse safety rails (network block, frozen clock, random seed, tmp_path redirects).
- Known factory/builder functions.

**Prefer reuse.** If `stocked_cart` or `mock_payments` already exists, use it. Do not reinvent `tmp_path` or `monkeypatch` — pytest provides them.

## Step 3: Derive the behavior list

Produce 5-12 bullets, each a behavior the contract promises. Include:

- Happy path(s).
- Each documented or raised exception.
- Each branch that changes an observable outcome.
- Boundary cases at the type level (empty collection, zero, negative, `None` if allowed).
- Idempotency / error-shape contracts for I/O-adjacent functions.

**Stop if the list would be speculation.** If the source is ambiguous, ask one clarifying question and wait. Do not write tests for behaviors you cannot read off the source.

Present the list to the user before writing. If auto mode, proceed but flag any bullet marked "inferred."

## Step 4: Write tests

One test per behavior. Apply the rules below.

### Naming

`def test_<subject>_<expected_behavior>():` — describes a behavior, not a function.

- Good: `test_empty_cart_total_is_zero`, `test_negative_quantity_raises`, `test_expired_token_refreshes_on_read`.
- Bad: `test_cart`, `test_1`, `test_add_works`.

### Structure

Arrange-Act-Assert, in that order. One Act per test. Comment the three phases only when whitespace alone is ambiguous.

### Contract over implementation

- Assert on return values, raised exceptions, observable side effects.
- **Never** read `_private` attributes, `__dict__`, or cached fields.
- A correct refactor of internals must leave the test green.

### Floats

`pytest.approx(expected, rel=1e-6)` for any non-integer arithmetic.

### Exceptions

`with pytest.raises(ExcClass, match=r"<pattern>"):` — always match.

### Parametrize

If the same logic is tested with different literals, use `@pytest.mark.parametrize`. Align the table so each row reads as a case. When inputs are nested dicts, long strings, or binary data, wrap them in `pytest.param(..., id="<readable-case-name>")` — autogenerated IDs appear in failure output and `-k` selection, so a readable ID cuts triage time. For simple scalars the default ID is fine.

### Fixtures

- Reuse first; define new fixtures only if ≥2 tests would share them.
- Function scope is the default. Widen only for expensive AND safe-to-share setup.

### Mocking

- For simple attribute, env-var, or chdir overrides, prefer pytest's `monkeypatch` fixture over `unittest.mock.patch`. `monkeypatch` auto-reverts at test teardown, does not create an accidental `MagicMock`, and demands an explicit replacement value. Reach for `patch` / `mocker.patch` only when you need a mock object (the test asserts on calls, return values, or side effects).
- Patch where the name is **used**, not where it is defined.
  - `from myapp.services.email import send` in `orders.py` → patch `myapp.orders.send`.
- Always pass `autospec=True` to `patch` / `patch.object`.
- Prefer a small fake class over `MagicMock` when the collaborator has ≥2 interactions.
- **Never** patch the SUT itself. The patch target must not be the function the test exercises.
- Assert on observable effects — not on `called_with(...)` kwargs that are not part of the contract.

### Determinism

- No raw `datetime.now()`, `time.time()`, `random.*`, `uuid.uuid4()`, network, or real FS.
- If the repo has autouse safety rails (found in Step 2), use them implicitly.
- If it does not, inject a clock / use `freeze_time` / seed `random` / use `tmp_path`, and note in the report that `python-test-quality:test-harden` would install these once.

### Speed

Target <50 ms per test. If unavoidable, mark `@pytest.mark.slow` and explain why in the report.

### Output file location

- Mirror the project's existing convention. If tests already live under `tests/`, write there; if they live alongside sources, do that. Do not impose a layout — detect the dominant one by scanning where existing `test_*.py` files sit relative to their sources.
- Name the file after the source module: `src/myapp/orders.py` → `tests/test_orders.py` (or `src/myapp/tests/test_orders.py` in a src-sibling layout).
- If `--out <path>` is in `$ARGS`, use that verbatim.
- If the target file exists, append new tests; do not overwrite.

## Step 5: Verify

Run `<prefix> -q <new test file>`.

- **Import errors / fixture-missing:** fix in the test file and re-run.
- **Assertion failures:** stop. Do **not** edit the SUT to make the test green. Report the red test — it is either a real bug the contract exposes, or the test is wrong. The user decides.

## Step 6: Report

```
## Target: <source>
## Tests written: <count> to <file>

### Pinned behaviors
 - test_<name>: <what it pins>
 ...

### Deliberately not tested
 - <behavior>: <why — e.g., "private helper", "language feature",
   "would require integration setup">

### Open questions about the contract
 - <ambiguity, if any>

### Suite state
 - <count> passing
 - <count> failing — stopped for author review (see output above)
 - Determinism safety rails: <installed / gaps — suggest test-harden
   if gaps>
```

## Rules

- **One behavior per test.** If a test has two Acts, split it.
- **No coverage padding.** Don't test the language. Don't test private helpers directly.
- **No SUT edits.** Red tests are findings, not triggers for production changes.
- **No best-effort assertions.** `assert result` alone is a smell; assert the specific value or shape.
- **Respect existing fixtures.** If the repo has a `mock_payments` fixture, use it — consistency across the suite matters more than micro-optimizing one test.

## Anti-goals

- Do not write tests that will go yellow on CI. If a behavior cannot be deterministically tested without `test-harden` first, say so and stop.
- Do not generate tests for symbols prefixed with `_` — they are not contract.
- Do not test logging strings or docstrings.
